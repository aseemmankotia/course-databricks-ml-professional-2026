## Chapter 4: Feature Engineering and Feature Store: Point-in-Time Correctness — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What two parameters must a feature table have to support point-in-time joins via FeatureLookup? | primary_keys AND timestamp_keys, both set at fe.create_table() time. Exam tip: omitting timestamp_keys means the table can only be joined on primary key alone (no time travel). |
| 2 | FeatureLookup parameter that enables an as-of (point-in-time) join instead of a plain key join? | timestamp_lookup_key — matches the label DataFrame's timestamp column against the feature table's timestamp_keys, returning the most recent feature value at or before that time. |
| 3 | fe.write_table mode='merge' vs mode='overwrite' — difference? | merge = upsert by primary key (update existing rows, insert new). overwrite = replace entire table contents. Exam tip: streaming/incremental batch jobs typically use merge. |
| 4 | What construct handles a feature that must be computed at inference time using an input that only exists in the serving request (e.g., current timestamp, request coordinates)? | FeatureFunction — wraps a Unity Catalog registered function, executed identically during training set creation and at model serving time, avoiding training/serving skew. |
| 5 | Which client/module replaced the legacy databricks.feature_store client for Unity Catalog? | databricks.feature_engineering — FeatureEngineeringClient (fe = FeatureEngineeringClient()) is the UC-integrated client with create_table/write_table/create_training_set/log_model. |
| 6 | How is label/feature leakage avoided when building a training set with FeatureLookup? | By using timestamp_lookup_key for an as-of join (no future feature values joined) and by passing exclude_columns to drop timestamp/label helper columns from the final feature set before training. |
| 7 | How are streaming feature tables populated? | fe.write_table(name=..., df=streaming_df, mode='merge') where streaming_df comes from a Structured Streaming readStream; the write itself runs as a continuous streaming query into the Delta-backed feature table. |
| 8 | create_training_set() key parameters? | df (base/labels DataFrame), feature_lookups (list of FeatureLookup objects), label (target column name), exclude_columns (columns to drop, e.g., timestamp keys). Returns a TrainingSet with .load_df(). |
| 9 | Batch feature vs streaming feature vs on-demand feature — when to use each? | Batch = periodically refreshed table (e.g., nightly aggregates). Streaming = continuously updated via Structured Streaming (near real-time). On-demand = computed at request time via FeatureFunction (needs request-only inputs). |
| 10 | What does Unity Catalog automatically capture for feature tables used in ML pipelines? | Lineage — links between feature tables, the training set/notebook/job that consumed them, and the resulting registered model, viewable in Catalog Explorer for governance/impact analysis. |
| 11 | What happens if you call fe.create_table without specifying timestamp_keys? | A standard (non-time-series) feature table is created — it can only be joined by primary key, not by timestamp_lookup_key. Exam trap: you cannot add timestamp_keys later without recreating the table. |
| 12 | How does score_batch / model serving retrieve feature values automatically at inference? | When a model is logged with fe.log_model (packaging the FeatureLookup/FeatureFunction metadata), Feature Engineering automatically performs the lookups/on-demand computations at fe.score_batch() or via Model Serving, so callers only need to supply primary keys and any on-demand inputs. |
